# TallyPulse code cleanup audit

Audit only. Nothing in the application, tests or configuration was changed for this report. This file is the only write.
Audited tree: branch `integration/ask-ai-consolidated`, HEAD `d6bad9c` (verified). Status labels: **Confirmed** (read in code or reproduced by a test run), **Suspected**, **Needs measurement**.

## 1. Executive summary

- The core is sound and should not be redesigned: the model only returns a plan, and validation, compilation and execution are deterministic and tenant-scoped; sync is idempotent; no require-cycles. This audit found no new security or data-integrity bug.
- The cleanup that is worth doing is small and mostly low-risk: the 3 test failures are stale test fixtures or patterns (not regressions), 78 private `check()` helpers, one CI gap, and two real duplications (error wrappers, Tally fetchers).
- Two earlier recommendations must be corrected after reading the code:
  1. **Deleting the two `handle()` wrappers is NOT behaviour-preserving.** They pass any 4xx message through; the central `errorHandler` replaces messages of errors that are not marked `userFacing` (section 4.1).
  2. **There is nothing to remove for `exceljs`**: it is in no manifest, lockfile or tracked file (the technical documentation already says so, line 721).
- The long `runSyncForCompanyModule` (335 lines) has genuinely different failure boundaries, but it is also the data-integrity path. Extract only with its existing tests as a net, and only if you are about to change it again.
- Top three tasks: see section 10.

## 4. Confirmed duplicate code

### 4.1 Error handling: partly duplicated, not interchangeable (P1, Confirmed)

- `backend/src/controllers/analyticsController.js:157 handle()` and `reportController.js:55 handle()` are the same wrapper; only the log label differs ("ANALYTICS ERROR" / "REPORT ERROR"). 20 catch blocks exist across 9 controllers (analytics 4, auth 6, chat 1, import 2, odbc 2, report 2, 1 each in sync recovery, sync status, voucher).
- A shared pattern exists: `middleware/errorHandler.js` (`userError`, `errorHandler`, `GENERIC_SERVER_ERROR`), used by auth, chat and import controllers.
- **Difference that matters:** the wrappers answer any error with `status` 400-499 using `error.message`. The central handler does that only when `err.userFacing === true`; otherwise a 4xx gets a generic status text. The analytics controller throws plain errors with `err.status = 400` (lines 44-99) and no `userFacing`. Deleting `handle()` as is would silently replace those validation messages with generic ones. The wrappers also omit the request id the central handler adds to 500s.
- **Smallest safe step:** leave the controllers alone, or first convert those throws to `userError(400, ...)` (or set `userFacing = true`), then delete the wrappers. Auth, import and odbc catch blocks serve different responsibilities (cleanup, specific messages) and should stay.
- **Risk:** medium (user-visible error bodies). **Tests:** `verify-security-audit.js` (no internal text leak, F-12), `verify-reports.js` (not in CI: needs a running backend), plus a new test that a 400 from analytics keeps its message.

### 4.2 Tally voucher fetchers (P1, Confirmed)

- `odbcService.js:690 getSalesVouchersSinceAlterId`, `:787 getPurchaseVouchersSinceAlterId`, `:888 getAdjustmentNoteVouchersSinceAlterId`.
- Sales vs purchase: the difference is the collection and filter names ("RTS Sales AlterID Collection" vs "RTS Purchase ..."), the function-name label passed to `requireVoucherTypeNames`, and the error log text. The purchase function's own comment says it "mirrors" sales and was kept separate deliberately "to match this file's existing style".
- Adjustment notes: same shape plus two extra Native Method fields (accounting allocations and bill allocations), proven in a live diagnostic.
- Pagination and filters are identical in structure (AlterID window via `afterAlterId`/`upToAlterId`).
- **Suggestion:** if consolidated, a small builder taking collection name, filter name and an optional extra field list is enough; keep the three exported names as one-line wrappers. Do not add a class hierarchy. **Not required for correctness.**
- **Risk:** medium: the Tally request text must stay byte-identical. **Protection:** a golden test of the three request bodies first (none exists); then `verify-sync-batching.js`, `verify-adjustment-note.js`, `verify-voucher-lifecycle.js` (the last needs live Tally: do not run).

## 7. AI planner and database observations

**Planner calls (Needs measurement).**
- Flow in `queryChat.js`: the query planner runs first; if it declines with `needs_analysis` (or an invalid/protocol-violation reply), `answerAnalysis` calls the analysis planner; `analysisPlanner.js:255` adds one bounded clarification retry when the scope already holds a period (`clarifyRetry`); investigation rounds can add `proposeWithModel` calls. So an analysis question can take 2 to 4 sequential calls, all through the same counted client.
- The planner response cache (`plannerResponseCache.js`: 500 entries, 100 per tenant, 24 h TTL, in-process) handles exact repeats; a hit is not counted as a model call. Concurrent identical requests share one call (coalescing).
- Provider requests including SDK retries are counted (`providerAttempts.js`), and an estimate is stored (`aiPricing.js`, only two models priced).
- None of this proves any call is unnecessary: the production telemetry that would show per-route call share and cost has not been collected. **Do not merge or remove planners yet.** Next step is measuring with `eval-ai-cost-report.js` after the usage records exist.
- Open product gap (Confirmed by code reading, not re-run live): in the analysis path nothing sets the `empty` flag or a pending question when every step is "Not run"; only the single-query paths do (around lines 560 and 617).

**MongoDB (Needs measurement).**
- Indexes on `Sale`: unique tenant + guid, tenant + voucherNo, tenant + status + voucherDate (`sales.model.js:148-164`); Purchase and AdjustmentNote similar. The compiled pipeline stages are `$match`, `$unwind`, `$addFields`, `$group`, `$sort`, `$limit`, `$project` (no `$lookup`). Product and customer breakdowns `$unwind` inventory after the `$match`, which an index cannot accelerate.
- `explain()` is used in one test only; no plan has been captured for real analytics pipelines. **Do not add or change indexes without a measured plan.**
- Mongoose builds indexes at start-up (no `autoIndex` setting in `src`); a risk only for large collections.

**Top three tasks to start with**
1. **Make the existing suite trustworthy:** update the two stale `verify-ask-ai-basic-questions.js` fixtures (add `lastSuccessAt` or the "not recorded" text) and the `verify-chat-timeout.cjs` regex to allow `signal`; add `verify-analysis-presentation.js` to CI and make CI discover suites by glob with a skip-list. Do not start with the sync worker split, planner merging, index changes or the helper migration.
